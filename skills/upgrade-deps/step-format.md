# The step format

The grammar of an upgrade's checklist, read by `upgrade.sh` and by the agent applying a step. What each kind
runs and owes is [`applying-a-step.md`](applying-a-step.md).

Every step carries an ID, its kind, the dependency, and the versions it moves between. IDs are `U01` upward
across the whole upgrade, assigned once, never renumbered.

**`upgrade.sh validate` checks the result** — a duplicate ID, an unrecognized kind, a line the kind does not
take, a line the kind owes, a placeholder value, a `files:` with no bullet under it, a `change:` naming no
place, a `needs:` naming a step nothing defines, an Open Question with no answer, a steps file with no log
beside it, an attempt or run-log entry left in the steps file, and in the log an attempt missing a line or its
evidence, a `B` entry outside `## Run Log` or numbered below the one before it, and a `kept back` entry
missing what kept it or what would unblock it. The script ships with the skill at
`scripts/upgrade/upgrade.sh` — under `${CLAUDE_PLUGIN_ROOT}` when installed as a plugin, under `.claude/` in a
plain checkout.

```
- [ ] U01 · bump · `org.assertj:assertj-core` 3.24.2 -> 3.26.3
  - files:
    - `gradle/libs.versions.toml`
  - guide: https://…/release-notes/3.26.3 — nothing breaking

- [ ] U02 · bump · `@types/node` 20.11.0 -> 20.14.2
  - files:
    - `package.json`
    - `package-lock.json`
  - guide: none found

- [ ] U03 · migrate · `org.springframework.boot` 3.2.5 -> 3.3.2
  - files:
    - `gradle/libs.versions.toml`
    - `src/main/resources/application.yml`
    - `src/main/java/…/KafkaConfig.java`
  - test-files:
    - `src/test/java/…/KafkaConfigTest.java`
  - guide: https://github.com/spring-projects/spring-boot/wiki/Spring-Boot-3.3-Release-Notes
  - change: `spring.kafka.listener.ack-mode` moves under `spring.kafka.listener.acknowledgment` · application.yml
  - change: `KafkaConfig` calls a constructor the release removed; the guide's replacement is the builder · KafkaConfig
  - needs: U01
  - docs: `<module>/docs/configuration.md`
```

| Line          | On which kinds | Holds                                                                                        |
|---------------|----------------|----------------------------------------------------------------------------------------------|
| `files:`      | all            | the manifest, the lock file, and every production file the step may edit, one per bullet     |
| `test-files:` | `migrate`      | every test file the step may edit, one per bullet                                            |
| `guide:`      | all            | the release notes or migration guide read for the step, and its verdict; or `none found`     |
| `change:`     | `migrate`      | one change the guide asks for and where in the module it lands; one line per change          |
| `needs:`      | any            | the step IDs whose bump this step's compile or run needs                                     |
| `docs:`       | any            | the pages the step invalidates — a configuration page, a conventions rule naming a version   |

**A `bump` carries no `change:` and no `test-files:`.** A bump that turns out to need either is a `migrate` and
goes back to the user re-classified.

**A `change:` names one guide item and one place.** Two places are two lines. What a `change:` line says is the
boundary of what the step may edit for it; a `kept back` entry in the log's `## Run Log` is where a `change:`
goes when it cannot be made.

**`files:` includes the lock file wherever the stack keeps one.** `package-lock.json`, `gradle.lockfile`,
`poetry.lock`, `Cargo.lock` — regenerated by the stack's own command, never edited by hand.

**A step in another steps file is named with that file** — `needs: shared/steps.md · U01`. `validate` does
not resolve what it cannot see; a bare ID always means this file, and `validate` refuses one no step here
defines. Given the upgrade's directory rather than one file, `validate` checks every steps file in it, each
with the log beside it.

**A dependency moving several majors is one step per major** where each has its own guide, `needs:` chaining
them, so a kept-back change names the release that asked for it.

**`docs:` is owed where a version is visible outside the manifest** — a conventions file that names it, a
configuration page whose keys a `change:` renamed, a README that quotes the version.
